可扩展远程执行架构（修订版）

不以 SSH 为根。中心是 Environment × Workspace × Runtime × CredentialBroker；SSH 只是第一个 Provider。

不考虑向后兼容；优先让 Bridge / 云 / Direct 后续只加插件、不改主干。

复盘初稿硬伤 Local 一等公民 Provider 可插拔 对齐 CC Environment SSH = 第一期交付

00 对上一版的复盘

初稿能做 MVP，但不适合长期扩展

根因：把 SSH 字段写进了 Session / Workspace API / UI 分支，Local 成了特例，连接方式与执行面绑死。

问题表现后果
SSH 渗入核心hostId、transport: local\|ssh加 Bridge/云要改 Session 与路由
Local 是特例if (remote) 到处都是两套路径，难测
连接=执行面SSH tunnel ≈ WorkerDirect/Bridge 生命周期塞不进
Controller 过载编排+SSH+鉴权+工具难替换
协议被 HTTP 绑架「少改前端」驱动架构核心形状不对

修订原则：先定不变式与端口；SSH 只是第一个 Environment Provider。

01 核心不变式

1
UI / 执行面分离

Chat、权限在 Control Plane；文件与工具在 Execution Plane。

2
Local 也是 Environment

没有「本地模式 vs 远程模式」两套代码；只有 kind 不同。

3
Session 绑 WorkspaceHandle

{ environmentId, cwd }，不是裸路径，也不是 optional remote?。

4
凭证不进 Execution Plane

经 CredentialBroker；Worker 只有短时票或隧道反代。

5
控制消息与数据消息正交

control_* 与 stream 共用 Runtime 通道，与 SSH/WS 无关。

6
Provider 可插拔

新远程形态 = 新 Provider；不改 Session / Agent Loop / Tool 语义。

02 概念模型

Environment

在哪跑？

local · ssh:… · bridge:… · cloud:…

Workspace

哪个目录？

/home/u/ws-code_index

Runtime

怎么说话？

stdio / WS / SSH 隧道上的同一协议

Connector = 环境如何可达（noop / SSH deploy / Bridge poll / 云 create）。与 Runtime 协议分离。

第一期产品

只是 Environment(ssh) + Workspace(dir) + Runtime(stream) + Connector(ssh)。主干已为其它 kind 留好位置。

03 分层架构

Clients: Picker · Chat · Permission │ Control API ▼ CONTROL PLANE SessionService · AgentOrchestrator · EnvironmentRegistry WorkspaceService · RuntimeBroker · CredentialBroker · PermissionGateway │ RuntimePort / FsPort ← 无 ssh import ▼ ENVIRONMENT PROVIDERS（插件） Local · Ssh · Bridge · Cloud · Direct │ ▼ EXECUTION PLANE = Agent Worker cwd · Tools · Sandbox · 无长期 API Key 只认 Runtime 协议，不认自己怎么被拉起

04 核心接口

type WorkspaceHandle = {
  environmentId: EnvironmentId  // "local" | "ssh:atsrws0049" | ...
  cwd: string                   // 环境内绝对路径
}

type Session = {
  id: string
  workspace: WorkspaceHandle    // 必有；不是 optional remote?
  // messages, permissionMode, ...
}

interface EnvironmentProvider {
  kind: EnvironmentKind
  list(): Promise<EnvironmentDescriptor[]>
  resolve(input: string): Promise<EnvironmentDescriptor>
  connect(env, opts?): Promise<EnvironmentConnection>
  disconnect(connectionId: string): Promise<void>
}

interface EnvironmentConnection {
  ensureWorker(version: string): Promise<WorkerInstallInfo>
  openRuntime(cwd: string, auth: RuntimeAuth): Promise<RuntimePort>
  openFs(): FsPort
  forwardPort?(port: number): Promise<LocalPortMapping>
}

Control Plane 从不 import ssh。SSH 细节关在 SshProvider 的 endpoint opaque 字段里。

05 主数据流（与 Provider 无关）

选 Environment + Folder → connect → ensureWorker → openFs().realpath → WorkspaceHandle → Session.bind(handle) → RuntimeBroker.getOrCreate → RuntimePort → CredentialBroker.issue Chat: Orchestrator → RuntimePort.send(user) → Worker tools（sandbox 在 Worker） → control_request → PermissionGateway → UI → control_response → Runtime → stream → Client

06 Providers 如何挂接

LocalProvider

一等公民。推荐始终 child worker，与远程同构，消灭特殊路径。

SshProvider（一期）

config → connect → deploy → ssh -R AuthProxy → RuntimePort / SFTP FsPort。

UI「Connect to Host」只是 kind=ssh 的皮肤。

BridgeProvider（后）

注册环境 + poll / ingress WS。无 SSH。Outbound 派活 + Inbound daemon 同一接口。

Cloud / Direct（后）

Cloud：API create + git 物化。Direct：已有 Worker URL，只协商版本。

07 Workspace / Sandbox

  • 废除到处传递「本机 path 字符串」
  • FS API 一律带 WorkspaceHandle，委派当前 connection 的 FsPort
  • Sandbox 校验只在 Worker 内
  • 换文件夹 = 新 Handle → 关旧 Runtime → openRuntime(newCwd)
  • 显示：atsrws0049:/home/u/ws-code_index

08 CredentialBroker

CC AuthProxy 的泛化：隧道只是到达 Broker 的一种方式。

CredentialBroker
  ├─ issueRuntimeAuth(sessionId, envId) → token
  ├─ AuthProxy (本地)     ← SshProvider -R
  └─ HTTP mint endpoint   ← Bridge / Cloud / Direct

Worker 只有 BAIX_RUNTIME_TOKEN + 可达的 BAIX_BROKER_URL。禁止长期 Key 写远端。

09 模块目录

硬规则

session/store、router、tools/* 禁止出现 sshHost / hostId。Session 只存 WorkspaceHandle。

10 第一期范围

做： LocalProvider（child worker）+ SshProvider + CredentialBroker + Picker + Session 绑 Handle。

不做： Bridge/Cloud/Direct 完整实现、IDE Extension Host、Web SSO 代持 SSH。

验收仍用 VS Code 场景，但验收的是平台上 kind=ssh 的一条 Provider 路径。

11 扩展检查清单

  1. 新 EnvironmentKind，还是现有 kind 的能力开关？
  2. 能否只实现/扩展一个 Provider？
  3. Workspace 是否仍是 { environmentId, cwd }？
  4. Runtime 是否仍走同一 RuntimePort 消息？
  5. 凭证是否仍只经 CredentialBroker？
  6. Session / Orchestrator / Chat 是否零改或只加展示？

若 2–6 任一条要改主干 → 先改 Provider 边界，禁止在 Session 上打补丁。

13 总结

Bottom line

好架构的中心不是 SSH，而是：

Environment × Workspace × Runtime × CredentialBroker，Provider 可插拔，Local 一等公民，Session 只绑 WorkspaceHandle。

第一期用 SshProvider 满足 VS Code 体验；之后远程需求优先加 Provider，禁止在 Session/Router 上长 if (remoteXxx)。
