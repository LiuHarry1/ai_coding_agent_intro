② Agent 核心循环 — 不是 Chat，是 Loop

Coding Agent 的本质：你写的循环驱动 LLM 多步决策，直到无 tool call 或达上限。

Chat vs Agent（代码里的差别）

普通 Chat一问一答，结束
Coding Agentquery() 内 for (step…) 循环，每步可能调工具
停止条件toolCalls.length === 0 → reason: 'completed'

一次用户 Turn 的调用链

POST /chat | stdio | ACP
  → runChatTurn()          turn/run-chat-turn.ts
  → prepareChatTurn()      注入 rules/skills/tools
  → runAgent() → query()   core/query.ts
       loop: preTurn → runStep → postTurn
  → runStep()              core/query/run-step.ts
       streamText + StreamingToolExecutor

单步 runStep 做什么

  1. 消息 sanitize → projectMessagesForApi
  2. streamText() 调 LLM（ai SDK + Provider）
  3. 有 tool_call → StreamingToolExecutor 执行
  4. buildToolMessage() 把结果 append 到 messages
  5. 经 wire 发 tool_call / tool_result 给 UI
建造要点：循环在 query()，不在模型里。Transport（HTTP/ACP）只调 runChatTurn()，不重复实现 loop。
src/core/query.ts · run-step.ts · turn/run-chat-turn.ts

③ 工具体系 — Agent 的「手」

LLM 只选工具；真正读写文件、跑命令、开浏览器，靠你注册的 ToolDefinition + 执行器。

注册与组装（每 Turn）

  1. 内置工具在 tools.ts → defaultRegistry
  2. prepareChatTurn 加载 MCP、子 Agent、Skill
  3. assembleToolPool() 分出 active / deferred
  4. deferred 过多时注入 ToolSearch 按需激活
  5. applyModeRestrictions 按 agent/ask/plan 过滤

约定：一工具一目录

tools/BashTool/
  BashTool.ts   → export definition
  prompt.ts     → 描述给 LLM 的 schema

执行与双路结果

组件职责
StreamingToolExecutor并发执行 tool calls
tool_execution.ts单工具 execute + 组装 ToolMessage
result 字符串给 LLM / 持久化 / compaction（精简投影）
resultBlocks含图片等时给模型的 blocks；UI 走 wire 完整内容
新增工具 = 实现 ToolDefinition + tools.ts 注册；不必改 query() 主循环。
src/tools.ts · assembleToolPool.ts · services/tools/

④ 上下文与记忆 — 脑容量管理

长任务会爆 context window；需要「注入规则 + 压缩历史 + 侧路记忆」三层配合。

四层分工（本仓库实现）

层机制何时生效
Project RulesAGENTS.md 向上合并每 turn 注入 system prompt
Auto Memoryservices/auto-memory/跨会话；turn 结束抽取 + prefetch
Session Memoryservices/session-memory/单会话笔记；compact 时消费
Compactionservices/compact/每 step 前 preTurn → compactIfNeeded

压缩触发点（代码路径）

  1. 每 step 前：preTurn() 调 compactIfNeeded
  2. 用户 /compact：runChatTurn 强制 compact 后返回
  3. Turn 结束：memory-lifecycle hooks 更新 session/auto memory
  4. 上下文超长：runStep 内 reactive compact + 重试

三档模型（静态绑定，非智能路由）

档位典型用途
large主 query() 循环、Plan、Compact
mediumSession memory 抽取、Auto memory
smallExplore 子 agent、session 标题、prefetch

⑤ 协议与多入口 — 引擎与 UI 解耦

先定 wire 消息形状，再写 HTTP / stdio / ACP 适配器；避免每个入口重写 Agent 逻辑。

protocol/ 单一真相源

  • OutgoingMessage：引擎 → 客户端（stream_event、tool_call、tool_result…）
  • IncomingMessage：客户端 → 引擎（user、control_response）
  • 握手：system/init + PROTOCOL_VERSION
  • 引擎边界：WireEmitter 发类型化消息，transport 只序列化

三种启动模式

模式入口Transport
默认npm startHTTP + SSE（/chat）
stdionpm run cliNDJSON 行协议
ACPnpm run acpJSON-RPC over stdio（IDE）

统一 Turn 宿主

无论哪种 Transport：
  都调用 runChatTurn({
    transport,   // SSE | noop | ACP 桥接
    runAgent,    // → query()
    session, cwd
  })

Session 持久化：JSONL
  src/session/store.ts
  tryBeginTurn() 同 session 禁止并发 turn
建造顺序建议：先实现 query() + WireEmitter + stdio；再加 HTTP SSE；最后做 ACP 薄适配。
protocol/ · core/wire-emitter.ts · turn/run-chat-turn.ts · entrypoints/cli.ts

⑥ 执行环境 — 工具在哪跑

控制面（HTTP Server / Agent 循环）与执行面（文件、Shell、LSP）分离；本地与 SSH 远程同构。

Execution Plane（控制面）

bootstrapExecutionPlane() 在 server 启动时初始化：

组件职责
EnvironmentRegistry注册 local / SSH Provider
RuntimeBroker按 workspace 管理 Worker 连接
CredentialBroker运行时认证

Worker 进程

  • src/worker/main.ts — stdio NDJSON RPC
  • 能力：FS 读写、Shell（前后台）、LSP、rg
  • 工具经 WorkerExecutionBackend 发 fs_op / lsp_op

Session 绑定工作区

session.workspace = {
  environmentId: 'local' | 'ssh:host',
  cwd: '/path/to/project'
}

prepareChatTurn → resolveExecutionBackend(session)
  → RuntimeBroker.getOrCreate()
  → Bash/Read/Grep 在对应 Worker 执行

远程时：plugins/skills 从控制机加载，
  文件/命令在远程 Worker 执行
建造要点：不要把 fs.readFile 散落在工具里；统一走 ExecutionBackend，日后加远程才不用改遍所有 Tool。
execution/bootstrap.ts · worker/main.ts · execution/resolve-backend.ts

⑦ 扩展机制 — 不改核心也能定制

子 Agent 分工、Skill 注入领域知识、MCP 接外部服务、磁盘配置热扩展。

子 Agent（Agent 工具）

  • 单一 Agent 工具，subagent_type 分发
  • 内置：Explore（只读·small）、Plan、general-purpose
  • 磁盘：.ai-agent/agents/*.md
  • 子循环：forked-agent 内再调 query()

Skill / Commands

  • .ai-agent/skills/ → Skill 工具按需加载
  • .ai-agent/commands/ → slash 展开或 fork
  • prepareChatTurn 里 registerSkills
  • 条件激活：匹配用户消息中的文件路径等

MCP / Plugins

  • settings.json → mcpServers
  • mcp-lifecycle 并入 registry
  • .ai-agent/plugins/ 可带 agents/skills/MCP
  • deferred MCP 工具经 ToolSearch 激活
权限模式 agent | ask | plan（permission-mode.ts）+ 主线程 agentType specialist 可限制工具 allowList / denyGlobs。
tools/AgentTool/ · skills/ · commands/ · core/mcp-lifecycle.ts · assembleToolPool.ts

⑧ 工程化 — 上线前要想清楚的事

能跑通 loop 只是第一步；生产环境还需要安全、并发、可观测、可部署。

安全与治理

  • permission-mode：ask 只读、plan 禁 mutating
  • AskUserQuestion + questions API（HITL）
  • Plan 审批：plan-approval-broker
  • sandbox.ts + can-use-tool 策略
  • Settings 分层：user / project / local / managed

并发与取消

  • tryBeginTurn：同 session 单 turn 互斥
  • /chat/cancel、/tool/abort
  • turn-abort-registry + abortSignal 传入 query()

可观测 & 部署

  • DUMP_PROMPTS=1 → JSONL prompt 轨迹（调试用）
  • telemetry / analytics/ 用量与成本
  • Docker：Web 与 Agent 分离（deploy/）
  • SSO：AUTH_ENABLED + JWT + workspace 锁定
  • 对外集成：client-sdk HTTP API
推荐落地顺序：① query + tools + stdio → ② HTTP/SSE + session → ③ compaction + 权限 → ④ Worker/远程 → ⑤ MCP/子 Agent → ⑥ 部署/SSO。
