0 结论：为什么必须是双路

每次工具 call() 成功后，原生结果 Out 会被投影成两条完全不同的消费路径——不是同一字符串画两遍。

路径字段 / 函数消费者设计目标
LLM 路 mapToolResult… → message.content API / 下一轮模型 完整载荷、行为指令、reminder、持久化指针、内部 ID
UI 路 toolUseResult → renderToolResultMessage Transcript / Ink / 搜索 摘要 chrome、diff、裸 stdout；屏蔽模型专用噪音
源码铁证 · transcriptSearch.ts

b.content 是 MODEL-facing serialization；UI 渲染 msg.toolUseResult——DIFFERENT text。若用模型文本做搜索：/malware 命中安全提醒，但屏幕上根本没有那行字（phantom）。

若只有大模型一路

Transcript 变成模型草稿纸；Edit 看不到 diff；Agent 的 agentId 和 “do not mention to user” 上屏；Bash 大输出变成 <persisted-output> 协议文案。下面用具体工具证明。

1 架构与写入点

tool.call() │ ▼ Out （原生结构化结果 = toolUseResult） │ ├──────────────────────────────┐ ▼ ▼ mapToolResultToToolResultBlockParam renderToolResultMessage │ │ ▼ ▼ message.content (tool_result) Ink / transcript UI │ ▼ normalizeMessagesForAPI → 只送 content （toolUseResult / mcpMeta 留本地，不进模型）

1.1 类型契约 · src/Tool.ts

  • mapToolResultToToolResultBlockParam — 唯一决定模型看到的 tool_result
  • renderToolResultMessage（可选）— transcript 长什么样；省略则不渲染（如 TodoWrite 走侧栏）
  • extractSearchText（可选）— 必须返回屏幕可见文本，禁止编入 system-reminder / persisted-output

1.2 同时写入 · toolExecution.ts

createUserMessage({
  content: contentBlocks,       // LLM：已 map 的 tool_result
  toolUseResult: toolUseResult, // UI：原生 Out
  mcpMeta: mcpMeta,             // SDK：never sent to model
})

1.3 UI 拒绝读 content · UserToolSuccessMessage.tsx

if (!message.toolUseResult || !tool) return null
tool.renderToolResultMessage?.(toolResult, …)

产品层已假设：没有 toolUseResult = 没有可展示的成功态。

1.4 为何不能共用一份字符串

约束LLM 路UI 路
长度可很长；过大则落盘必须短、可扫
指令注入需要 reminder /「勿提 ID」绝不能显示
结构压成 API blocks需要 structuredPatch / stdout 等字段
搜索无关必须与像素一致

2 四种分流模式

模式含义代表
A. 反转载荷模型拿全文；UI 只拿 chromeFileRead, WebSearch, WebFetch
B. 反转 ACK模型拿一句话；UI 拿完整 diffFileEdit, FileWrite
C. 同源不同包装都基于 stdout/命中，模型多包装Bash, Grep, Glob
D. 指令侧信道模型拿编排指令；UI 拿状态/侧栏Agent, TodoWrite, Skill

A/B 是「必须双路」的铁证；C/D 说明即使数据同源，序列化目标不同也不能合并。

3 按工具：双路内容 + 只有 LLM 路会怎样

3.1 FileRead（模式 A）— 最强反例

LLM 路

带行号全文 + CYBER_RISK_MITIGATION_REMINDER + 空文件 <system-reminder>；图片为 base64 block

UI 路

仅 Read N lines / Read image (42KB) — 从不展示正文

只有 LLM 路 · 举例

读 800 行 auth.ts → 页面刷出整文件 + 安全提醒。对话变成代码瀑布；搜 malware 命中提醒文案但屏幕无对应行（phantom）。图片则吐出巨量 base64。

说服点

产品语义是「知道读了什么、多少行」；模型语义是「这是文件内容，请推理」。不可共用文本。

3.2 FileEdit / FileWrite（模式 B）— 另一极

LLM 路

The file payment.ts has been
updated successfully.

UI 路

完整彩色 diff，依赖 Out 里的 structuredPatch / 原文——这些字段从不进入 mapped ACK。

只有 LLM 路 · 举例

改了计费逻辑 → 页面只剩一句 ACK → 用户无法审查任何 diff。从 ACK 字符串还原不了 patch。UI 路是审查数据的唯一通道，不是美化。

3.3 Bash（模式 C）

LLM 路

stdout/stderr + 中断标签 + backgroundInfo（含 task ID）+ 大输出改写为 <persisted-output> 预览

UI 路

直接渲染裸 stdout/stderr。源码注释：UI never shows persistedOutputPath wrapper, backgroundInfo

只有 LLM 路 · 举例

npm test 输出 2MB → 模型看到 preview + 磁盘路径协议；若 UI 渲染同一段，用户看到 XML 包装器而非真实测试日志，或误以为命令只输出了 preview 那么点。

3.4 Grep / Glob

模型拿命中全文以便继续定位；UI 默认 Found N files chrome。只有 LLM 路时，一次宽 Grep 把成百上千行砸进 scrollback，verbose 开关失效。

3.5 WebSearch（模式 A）

LLM 路

Web search results for query: "…"
Links: […]
REMINDER: You MUST include the
sources above … markdown hyperlinks.

UI 路

仅 Did N searches in Xs。extractSearchText 故意返回空串。

只有 LLM 路 · 举例

用户看见整页链接 JSON + 「你必须用 markdown 引用」——这是对模型的引用纪律，不是给人看的结果页。

3.6 WebFetch

模型拿页面正文；UI 默认 Received 42KB (200 OK)。只有 LLM 路：每次 fetch 把整页灌进 transcript。

3.7 Agent（模式 D）— 隐私与编排

LLM 路（异步启动节选）

agentId: xxx (internal ID - do not
mention to user. Use SendMessage
with to: 'xxx' to continue…)

UI 路

Done (N tool uses · tokens · duration) / Backgrounded agent 统计 chrome

只有 LLM 路 · 举例

页面明文出现 agentId 和 “do not mention to user”——产品自己打脸；用户被 mailbox 协议污染。

说服点

这里双路是 need-to-know 信息隔离：编排元数据只给父 agent，不给人类。

3.8 TodoWrite（模式 D）

模型拿「继续用 todo」+ 可能的 verification nudge；UI 不实现 renderToolResultMessage——结果进 todo 面板（Out 的 oldTodos/newTodos）。只有 LLM 路：要么刷说教话术，要么丢面板数据。

3.9 NotebookEdit / Skill / MCP

  • NotebookEdit：模型扁平字符串；UI 高亮代码块。
  • Skill：模型 “Launching skill…”；UI “Successfully loaded skill”。
  • MCP：另有 mcpMeta（_meta / structuredContent）第三条旁路，永不送模型。只有 LLM 路则 SDK 宿主与富渲染双损。

4 「只有大模型一路」的总账

#后果直接原因
1Transcript 不可用Read/Search/Fetch 全文 + Bash 包装器淹没对话
2无法做变更审查diff 只在 Out，不在 mapped ACK
3搜索说谎（phantom）索引 reminder / background / persisted-output
4内部编排泄漏Agent agentId、「勿告知用户」上屏
5大输出 UX 错误人看到持久化协议而非真实 stdout
6行为指令污染 UIWebSearch REMINDER、Todo nudge 像故障文案
7SDK/MCP 宿主受损mcpMeta / 结构化 Out 无法从纯字符串还原
8Resume 渲染脆弱UI 依赖 outputSchema.safeParse(toolUseResult)
9子 agent 内存策略失效今日可丢掉子 agent 的 toolUseResult，只留 mapped content
对称失败

若只有 UI Out、不做 map：模型丢掉 reminder、continuation ID、persisted 指针、空结果防呆、Edit 短 ACK——agent 循环质量同样崩。双路是双向刚需。

5 反方意见与驳回

「让模型也看 UI 摘要？」

不够推理：Read 只说「42 行」无法改代码；Edit 只给 diff 会重复占上下文，且缺少「用户改过你的提案」等元信息通道。

「让 UI 从 tool_result 再解析？」

map* 有意丢弃 structuredPatch、完整 todos、超大 stdout。从 ACK 反解 diff 不可能；为 UI 剥离 reminder 又是脆弱字符串协议。原生 Out 才是 UI 的 source of truth。

「这不是重复存储浪费吗？」

子 agent 可丢 toolUseResult；进 API 前本来就丢掉 UI 字段。换来正确的人机界面 + 正确的模型控制面。本质是 CQRS：一次写入，两种读模型。

一句话记住

Out 是事实；map 是给模型的简报+指令；render 是给人的工作台视图。取消双路 = 强迫人类读模型简报，或强迫模型读人类摘要——同时失去「能干活」和「能被信任地看着干活」。
