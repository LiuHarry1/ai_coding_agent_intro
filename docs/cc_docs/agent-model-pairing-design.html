大小模型搭配框架

核心约束：大模型与小模型的 provider / baseURL / apiKey / model 都可能不同。

因此不能只在同一 profile 上加 smallFastModel 字符串，而要做成两条独立的 LLM Profile + 双 Provider 运行时。

双 Profile 对齐 Claude Code 任务切分 向后兼容现有 provider

01 约束与原则

维度是否可不同含义
provider是如 main=anthropic，small=openai-compatible
baseURL是不同网关 / 区域 / 代理
apiKey是不同账号或网关鉴权
model是opus vs haiku / gpt vs qwen
thinking建议仅 main旁路默认 off，避免贵且慢
  1. 按任务选通道，不做请求内动态路由（同 CC）。
  2. Compact / 主 Agent / 安全分类永远走 main。
  3. 旁路永远走 smallFast（除非 sideQuery 显式指定其它 lane）。
  4. 缺省继承：小模型配置可只写差异字段，其余从 main 继承，降低配置负担。
  5. 未配置 smallFast：回退到 main（打 warning），保证不炸。

02 配置形态

保持现有 provider 作为主模型（零迁移成本），新增可选 smallFastProvider。

// core/types.ts — AppConfig
export interface AppConfig {
  /** 主循环模型（现有字段，不变） */
  provider: LlmProfile

  /**
   * 小快模型通道。可写完整 profile，也可只写差异字段。
   * 未配置时运行时回退到 provider（main）。
   */
  smallFastProvider?: Partial<LlmProfile>

  compaction: CompactionConfig
  mcpServers: Record<string, MCPServerConfig>
  lspServers: Record<string, LspServerConfig>
  disabledTools?: string[]
}

// LlmProfile 本身不变 —— 两边复用同一形状
export interface LlmProfile {
  provider: ProviderId      // 'openai' | 'anthropic' | 'openai-compatible'
  name?: string
  baseURL: string
  apiKey: string
  model: string
  thinking: ThinkingConfig // smallFast 解析后强制/默认 off
}

为何不用 smallFastModel: string

那种写法假定同 endpoint。你们明确要支持不同 URL / key / provider，必须是第二份 profile（或可 partial 继承的第二份）。

03 解析与继承

建议新建 core/llm/resolveModelPair.ts：

export type ModelLane = 'main' | 'smallFast'

export interface ResolvedModelPair {
  main: LlmProfile
  smallFast: LlmProfile
  /** smallFast 是否回退到了 main（用于日志/告警） */
  smallFastFellBackToMain: boolean
}

/**
 * smallFastProvider 缺省字段从 main 继承。
 * thinking：旁路一律 off（除非显式写了 thinking）。
 */
export function resolveModelPair(config: AppConfig): ResolvedModelPair {
  const main = resolveProfile(config.provider)

  if (!config.smallFastProvider) {
    return {
      main,
      smallFast: { ...main, thinking: { mode: 'off' } },
      smallFastFellBackToMain: true,
    }
  }

  const merged = {
    ...profileToRecord(main),
    ...config.smallFastProvider,
    // 旁路默认关 thinking；仅当用户显式配置了 thinking 才保留
    thinking: config.smallFastProvider.thinking ?? { mode: 'off' },
  }
  const smallFast = resolveProfile(merged)
  return { main, smallFast, smallFastFellBackToMain: false }
}

继承规则（直观）

smallFastProvider 写了什么结果
什么都不写完全等于 main（warning）
只写 model同 provider/URL/key，换 model id
写 baseURL + model同 provider/key（继承），换网关与模型
四件套全写完全独立第二条链路
写了不同 provider走另一套 strategy（anthropic / openai / openai-compatible）

04 运行时对象

settings.json │ ▼ resolveModelPair(config) │ ├─ main: LlmProfile ──────► buildProvider(main) → IProvider (main) └─ smallFast: LlmProfile ► buildProvider(smallFast) → IProvider (smallFast) │ ▼ LlmRuntime { pair: ResolvedModelPair main: IProvider smallFast: IProvider lane(lane): { profile, provider } }
// core/llm/runtime.ts
export interface LlmRuntime {
  pair: ResolvedModelPair
  main: IProvider
  smallFast: IProvider
}

export function buildLlmRuntime(config: AppConfig): LlmRuntime {
  const pair = resolveModelPair(config)
  if (pair.smallFastFellBackToMain) {
    console.warn('[llm] smallFastProvider unset; falling back to main provider')
  }
  return {
    pair,
    main: buildProvider(pair.main),
    smallFast: buildProvider(pair.smallFast),
  }
}

export function laneOf(rt: LlmRuntime, lane: ModelLane) {
  return lane === 'main'
    ? { profile: rt.pair.main, provider: rt.main }
    : { profile: rt.pair.smallFast, provider: rt.smallFast }
}

请求作用域

现在 run-chat-turn.ts 里是 buildProvider(resolvedSettings.config.provider)。 改为一次构建 buildLlmRuntime(config)，把整个 runtime 往下传（agent / compact / 旁路 helper）， 避免每次旁路再读 settings、也避免 main/small 不一致。

05 调用 API（对齐 CC）

querySmallFast ≈ queryHaiku

强制走 smallFast 通道：该通道自己的 provider + model，thinking off，无 tools。

export async function querySmallFast(opts: {
  runtime: LlmRuntime
  system?: string
  prompt: string
  abortSignal?: AbortSignal
  maxTokens?: number
  querySource: string   // 用量归因
}): Promise<string> {
  const { profile, provider } = laneOf(opts.runtime, 'smallFast')
  const result = await generateText({
    model: provider.chatModel(profile.model),
    system: opts.system,
    prompt: opts.prompt,
    maxOutputTokens: opts.maxTokens ?? 1024,
    abortSignal: opts.abortSignal,
    // 故意不带 main 的 streamTextExtras / thinking
  })
  // telemetry: { lane: 'smallFast', model, provider, querySource, usage }
  return result.text
}

sideQuery ≈ sideQuery

旁路管道；默认 smallFast，也可显式选 main，或传入临时 profile（极少用）。

export async function sideQuery(opts: {
  runtime: LlmRuntime
  /** 默认 'smallFast' */
  lane?: ModelLane
  system?: string
  messages: ...
  tools?: ...
  maxTokens?: number
  abortSignal?: AbortSignal
  querySource: string
}): Promise<...> {
  const lane = opts.lane ?? 'smallFast'
  const { profile, provider } = laneOf(opts.runtime, lane)
  return generateText({
    model: provider.chatModel(profile.model),
    ...
  })
}

09 落地阶段

P0
双 Profile + Runtime 骨架 AppConfig / settings merge / resolveModelPair / buildLlmRuntime；chat turn 改用 runtime.main。行为可与现在一致（未配 smallFast 时回退）。
P1
querySmallFast + 会话标题 第一个真实旁路；验证不同 URL/key/provider 都能通；telemetry 带 lane。
P2
更多旁路 + UI 设置 away summary、WebFetch 抽取；settings API / 前端可编辑 smallFastProvider。
P3
sideQuery(lane) + 安全类任务 需要主模型旁路时用 lane:'main'；子代理可选 smallFast。

和 CC 的差异（刻意的）

CC 的 Small Fast 主要是同账号下换 Haiku model id（Bedrock 最多换 region）。 你们需要整条链路可替换，所以框架升一级：双 LlmProfile + 双 IProvider。 任务切分白名单仍完全对齐 CC。
