LSP 架构与用法

这份文档总结当前 coding agent 中新增的 LSP 能力：它为什么存在、怎么接入 agent、怎么配置、怎么在真实写代码时发挥作用，以及如何测试。

目的 架构 流程图 同步/异步 调用流程 配置 用法 诊断反馈 测试

1. LSP 的目的

LSP 不是让网页编辑器获得鼠标悬停弹窗，而是给 coding agent 增加一组“语义代码理解工具”。以前 agent 主要靠 Grep、Glob、Read 搜文本和读文件；现在它可以通过语言服务器询问更精确的问题。

hover 类型信息 go to definition find references document/workspace symbols diagnostics feedback
真实价值： 当 agent 要改接口、重构函数、追踪类型、修类型错误时，LSP 可以减少“猜”和纯文本搜索带来的误判。

2. 总体架构

settings.json

用户在 .ai-agent/settings.json 中配置 lspServers。

LSP Tool

模型通过 deferred 的 LSP 工具发起 hover、definition、references 等请求。

Workspace Manager

按 workspace 和配置 hash 缓存 manager，并按文件扩展路由到 server。

Language Server

通过 stdio JSON-RPC 与真实语言服务器通信。

核心文件

  • src/services/lsp/client.ts: stdio JSON-RPC 客户端。
  • src/services/lsp/server-instance.ts: 单个 language server 生命周期。
  • src/services/lsp/server-manager.ts: 扩展名路由、文件同步、诊断注册。
  • src/services/lsp/manager.ts: workspace-scoped manager 缓存和 shutdown。
  • src/tools/LSPTool/LSPTool.ts: agent 可调用的 LSP 工具。

接入点

  • core/settings-manager.ts: 读取并合并 lspServers。
  • prepare_chat_turn.ts: 将 LSP 配置传给工具上下文。
  • tools/FileWriteTool/FileWriteTool.ts 和 tools/FileEditTool/FileEditTool.ts: 写入后同步 didChange/didSave。
  • core/agent.ts: 每个 step 前注入新的 LSP diagnostics。
  • server/index.ts: 进程退出时关闭 LSP 子进程。

4. 同步与异步时序

同步 await LSP 查询

hover、go_to_definition、find_references 等 request 型操作都是同步等待结果的。这里的“同步”不是阻塞整个 Node 进程，而是当前 tool call 会 await promise，模型要等 tool result 回来后才能继续下一步。 

agent calls LSP tool
→ await manager.sendRequest(...)
→ await server.sendRequest(...)
→ await JSON-RPC response
→ return tool result
→ model continues

异步 notification 诊断反馈

didChange、didSave 和 publishDiagnostics 是 notification/反馈链路。写文件工具不会等 TypeScript server 完成诊断；诊断稍后到达后会进入 registry。 

Write/Edit returns to model
→ language server later publishes diagnostics
→ diagnostics registry stores them
→ next agent step drains registry
→ system-reminder is injected

懒启动 第一次请求会更慢

server 不在 npm start 时启动。第一次查询某个扩展名，或者第一次编辑需要同步到某个 language server 时，才会执行 ensureServerStarted()。所以第一次 hover 可能包含启动、initialize、indexing 的开销；后续复用同一个 workspace manager，会快很多。 

first .ts LSP request
→ no server running
→ spawn npx typescript-language-server --stdio
→ initialize workspace
→ send actual LSP request

later .ts LSP request
→ reuse existing server
→ send request directly

5. 一次 hover 的调用流程

  1. 用户让 agent 查询某个文件某个位置的类型或文档。
  2. 如果 LSP 是 deferred tool，模型先用 ToolSearch 加载它。
  3. LSP 工具读取 file_path、line、character。
  4. getLspManager(cwd, lspServers) 获取当前 workspace 的 manager。
  5. manager 按扩展名，比如 .ts，选择 TypeScript server。
  6. 如果 server 还没启动，server-instance 会懒启动 language server 并发送 initialize。
  7. 工具先发送 textDocument/didOpen，再发送 textDocument/hover。
  8. 返回结果被格式化成纯文本，作为 tool result 给模型继续推理。
用户请求
  → ToolSearch 激活 LSP
  → LSP({ operation: "hover", file_path, line, character })
  → LspServerManager
  → LspServerInstance
  → LspClient
  → typescript-language-server --stdio
  → hover result

6. 配置方式

LSP server 配置放在项目的 .ai-agent/settings.json 中。当前项目已经配置了 TypeScript LSP： 

{
  "lspServers": {
    "typescript": {
      "command": "npx",
      "args": ["--yes", "typescript-language-server", "--stdio"],
      "extensionToLanguage": {
        ".ts": "typescript",
        ".tsx": "typescriptreact"
      },
      "startupTimeout": 30000
    }
  }
}
字段 作用
command 启动 language server 的命令。Windows 下当前实现使用 shell spawn，因此 npx 可用。
args 传给命令的参数，例如 --stdio。
extensionToLanguage 文件扩展名到 LSP language id 的映射，也是 manager 路由 server 的依据。
startupTimeout 初始化超时时间，避免 language server 卡住 agent。
env / workspaceFolder / initializationOptions 可选字段，用于给特定 language server 传环境变量、工作区路径和初始化参数。

7. Agent 怎么使用 LSP

Hover

查询某个位置的类型、签名或文档。

{
  "operation": "hover",
  "file_path": "src/core/types.ts",
  "line": 446,
  "character": 18
}

Go To Definition

找当前位置符号的定义位置。

{
  "operation": "go_to_definition",
  "file_path": "src/core/types.ts",
  "line": 446,
  "character": 18
}

Find References

找某个符号的引用，适合重构前看影响面。

{
  "operation": "find_references",
  "file_path": "src/core/types.ts",
  "line": 446,
  "character": 18
}

推荐提示词

在聊天里可以这样让 agent 使用 LSP：

先用 ToolSearch 加载 LSP 工具。
然后对 src/core/types.ts 里的 AppConfig 执行 hover，
再查找它的 references，告诉我哪些地方依赖这个配置类型。

或者在复杂修改前这样说：

这次修改涉及类型和跨文件引用。
请优先用 LSP 的 hover / go_to_definition / find_references 理解影响面，
再开始编辑。

8. 写代码时的诊断反馈

当前 LSP 不只是查询工具，也会在 agent 写文件后同步给 language server。成功执行 Write 或 Edit 后，会触发： 

clear delivered diagnostics
→ textDocument/didChange
→ textDocument/didSave
→ language server publishDiagnostics
→ diagnostics registry
→ next agent step system-reminder

诊断消息在 src/utils/attachments/lsp-diagnostics.ts 中被转换为普通 system-reminder 用户消息，注入到后续模型上下文里。

这意味着 agent 写完代码后，如果 TypeScript server 报“属性不存在”“类型不匹配”“缺少 import”等问题，下一步模型可以直接看到并继续修。

9. 如何测试

启动前检查

  1. 确认 .ai-agent/settings.json 有 lspServers。
  2. 运行 npm install，确保依赖存在。
  3. 运行 npm run typecheck，确认代码编译通过。
  4. 运行 npm start 启动 agent server。

聊天内测试

  1. 让 agent 用 ToolSearch 加载 LSP。
  2. 对一个 .ts 文件执行 hover。
  3. 再执行 go_to_definition 或 find_references。
  4. 让 agent 故意制造一个小的 TypeScript 类型错误，观察下一步是否收到 diagnostics。

底层验证命令

之前已经用下面等价方式验证过 TypeScript LSP hover 能返回结果：

npx typescript-language-server --stdio
textDocument/hover
→ LSP hover verification: ok

10. 限制和注意点

  • 当前是 agent 工具能力，不是网页编辑器的鼠标 hover 弹窗。
  • LSP tool 是 deferred，模型通常需要先通过 ToolSearch 激活。
  • 只实现了 stdio transport，没有实现 socket transport。
  • diagnostics 是文本 system-reminder，暂未做前端专用诊断卡片。
  • LSP diagnostics 不能完全替代 npm run typecheck，复杂构建错误仍应跑项目命令验证。
  • 如果多个 server 支持同一扩展名，当前使用第一个匹配的 server。

11. 一句话总结

这个 LSP 实现给 coding agent 增加了“语义代码理解”和“写后诊断反馈”能力：它让 agent 在真实写代码时可以先问语言服务器理解类型和引用，再编辑文件，编辑后再根据语言服务器 diagnostics 继续修正。
