LSP 架构与用法

这份文档对齐当前 coding agent 的 LSP 实现：stdio 语言服务器栈、deferred LSP 工具、写后 diagnostics 附件反馈，以及通过 stpl-lsp-bridge 接入 STPL Language Server。

目的 架构 流程图 同步/异步 调用流程 配置 STPL Bridge 用法 诊断反馈 测试

1. LSP 的目的

LSP 不是给网页编辑器做鼠标悬停弹窗，而是给 coding agent 增加一组“语义代码理解工具”。以前 agent 主要靠 Grep、Glob、Read 搜文本和读文件；现在它可以通过语言服务器询问更精确的问题。

hover go_to_definition find_references document / workspace symbols go_to_implementation diagnostics attachment
真实价值： 当 agent 要改接口、重构函数、追踪类型、修类型错误，或处理 STPL .spec / .flow 等 DSL 时，LSP 可以减少纯文本搜索带来的误判。

2. 总体架构

settings.json

在 .ai-agent/settings.json 配置 lspServers（含 TS / Python / Java / STPL 等）。

LSP Tool

模型通过 deferred 的 LSP 工具发起 hover、definition、references 等请求。

Workspace Manager

按 workspace + config hash 缓存 manager，按扩展名路由 server；相对脚本路径相对 agent 包根解析。

Language Server

stdio JSON-RPC。普通 LS 直接 spawn；STPL 经 bridge 再连 SWC JVM。

核心文件

  • src/services/lsp/client.ts：stdio JSON-RPC 客户端。
  • src/services/lsp/server-instance.ts：单个 language server 生命周期、initialize、restart。
  • src/services/lsp/server-manager.ts：扩展名路由、文件同步、resolveAgentRelativePath。
  • src/services/lsp/manager.ts：workspace-scoped manager 缓存与 shutdown。
  • src/services/lsp/passiveFeedback.ts：注册 publishDiagnostics 通知处理。
  • src/services/lsp/LSPDiagnosticRegistry.ts：pending / delivered 诊断去重与限流。
  • src/tools/LSPTool/LSPTool.ts：agent 可调用的 LSP 工具。
  • integrations/stpl-lsp-bridge/：STPL 的 stdio ↔ TCP reverse-connect bridge。

接入点

  • core/settings-manager.ts：读取并合并 lspServers。
  • utils/processUserInput/prepare_chat_turn.ts：把配置写入 ToolContext.lspServers。
  • tools/FileWriteTool/FileWriteTool.ts / FileEditTool.ts：写入后 fire-and-forget didChange / didSave。
  • utils/attachments.ts：每步收集 diagnostics attachment。
  • utils/messages.ts：attachment 展开为 <new-diagnostics> system-reminder。
  • core/agent.ts：step 前后调用 getAttachmentMessages。
  • server/index.ts：进程退出时 shutdownAllLspManagers()。

4. 同步与异步时序

同步 await LSP 查询

hover、go_to_definition、find_references、document_symbol、workspace_symbol、go_to_implementation 都是同步等待结果。这里的“同步”不是阻塞整个 Node 进程，而是当前 tool call 会 await promise，模型要等 tool result 回来后才能继续下一步。 

agent calls LSP tool
→ await manager.sendRequest(...)
→ await server.sendRequest(...)
→ await JSON-RPC response
→ return tool result
→ model continues

异步 notification 诊断反馈

didChange、didSave 和 publishDiagnostics 是 notification/反馈链路。写文件工具不会等 language server 完成诊断；诊断稍后到达后会进入 registry，再在下一步变成 diagnostics attachment。 

Write/Edit returns to model
→ language server later publishes diagnostics
→ LSPDiagnosticRegistry stores them
→ next agent step drains via attachments.ts
→ messages.ts expands to system-reminder

懒启动 第一次请求会更慢

server 不在 npm start 时启动。第一次查询某个扩展名，或者第一次编辑需要同步到某个 language server 时，才会执行 ensureServerStarted()。STPL 首次启动还会包含 JMX discover / start / reverse-connect，通常比本地 TypeScript server 更慢。 

first matching-extension LSP request
→ no server running
→ spawn command/args (maybe bridge)
→ initialize workspace
→ send actual LSP request

later same-extension request
→ reuse existing server
→ send request directly

5. 一次 hover 的调用流程

  1. 用户让 agent 查询某个文件某个位置的类型或文档。
  2. 如果 LSP 是 deferred tool，模型先用 ToolSearch 加载它。
  3. LSP 工具读取 file_path、line、character（1-based）。
  4. getLspManager(cwd, lspServers) 获取当前 workspace 的 manager。
  5. manager 按扩展名选择 server（例如 .ts → typescript，.spec → stpl）。
  6. 如果 server 还没启动，server-instance 会懒启动并发送 initialize。
  7. 若文件未打开且不超过 10MB，工具先 didOpen，再发送 textDocument/hover。
  8. 返回结果被格式化成纯文本，作为 tool result 给模型继续推理。
用户请求
  → ToolSearch 激活 LSP
  → LSP({ operation: "hover", file_path, line, character })
  → LspServerManager
  → LspServerInstance
  → LspClient
  → language server (or stpl-lsp-bridge → SWC)
  → hover result

6. 配置方式

LSP server 配置放在 .ai-agent/settings.json。完整示例见 .ai-agent/settings.example.json，可同时配置多种语言： 

{
  "lspServers": {
    "typescript": {
      "command": "npx",
      "args": ["--yes", "typescript-language-server", "--stdio"],
      "extensionToLanguage": {
        ".ts": "typescript",
        ".tsx": "typescriptreact"
      },
      "startupTimeout": 30000
    },
    "python": {
      "command": "npx",
      "args": ["--yes", "pyright-langserver", "--stdio"],
      "extensionToLanguage": {
        ".py": "python",
        ".pyi": "python"
      },
      "startupTimeout": 30000
    },
    "stpl": {
      "command": "node",
      "args": ["integrations/stpl-lsp-bridge/index.js"],
      "env": {
        "STPL_START_MODE": "jmx",
        "STPL_AUTO_DISCOVER": "true",
        "STPL_STATUS_FILE": ".ai-agent/stpl-status.json",
        "STPL_JMX_HELPER": "integrations/stpl-lsp-bridge/jmx-helper/StplJmxHelper.java",
        "STPL_CONNECT_TIMEOUT_MS": "60000"
      },
      "extensionToLanguage": {
        ".spec": "stpl",
        ".flow": "stpl",
        ".dbd": "stpl",
        ".prog": "stpl",
        ".seq": "stpl",
        ".pat": "stpl"
      },
      "startupTimeout": 120000,
      "maxRestarts": 1
    }
  }
}
字段 作用
command 启动 language server 的命令。绝对路径 / PATH 上的 bare command（如 npx、jdtls）保持原样；相对路径按 agent 包根解析。
args 传给命令的参数。相对脚本路径同样相对 agent 包根解析，因此 spawn cwd 是用户 workspace 时，integrations/stpl-lsp-bridge/index.js 仍可找到。
extensionToLanguage 文件扩展名到 LSP language id 的映射，也是 manager 路由 server 的依据。缺此字段的配置会被跳过。
startupTimeout initialize 超时时间，避免 language server 卡住 agent。
maxRestarts 崩溃后允许的重启次数（默认 3）。STPL 建议设为 1，因为 SWC 同时只允许一个 LS client。
env / workspaceFolder / initializationOptions 可选字段，用于环境变量、工作区路径和初始化参数。
若同一扩展名被多个 server 声明，当前实现使用 第一个匹配 的 server。例如想暂时禁用某个 Java server，可把其 extensionToLanguage 改成 _extensionToLanguage（settings.example 里的 jdtls 即此写法）。

7. STPL Bridge

Agent 的 LSP 客户端只支持 stdio。STPL Language Server 跑在已启动的宿主 IDE（SWC）JVM 里，通过 JMX 触发、TCP reverse-connect 通信。因此仓库内置 integrations/stpl-lsp-bridge，对外伪装成普通 command。 

Agent lspServers.stpl
  → node integrations/stpl-lsp-bridge/index.js   (stdio LSP)
    → listen 127.0.0.1:port
    → arm accept listener
    → JMX serverInfo (preflight / discover)
    → JMX start(pid, port)
    → accept one socket
    → bidirectional byte pipe
    → SWC JVM language server

对接范围

  • 使用：SWC 内嵌 + JMX（STPL_START_MODE=jmx）。
  • 不对接：standalone stplls_start.sh / headless 一键启动。
  • wait-for-connect 仅用于 debug / mock smoke。

关键环境变量

  • STPL_AUTO_DISCOVER：扫描本机 JVM 找 STPL MBean。
  • STPLLS_PID：可选；discover 失败时手工指定。
  • STPL_STATUS_FILE：缓存 pid / workspace。
  • STPL_JMX_JAVA / STPL_JMX_HELPER：JMX helper 运行时。
Agent workspace 路径应与 SWC Eclipse workspace 一致。更细的对接说明见 docs/stpl-lsp-integration-requirements.md 与 integrations/stpl-lsp-bridge/README.md。

9. 写代码时的诊断反馈

当前 LSP 不只是查询工具，也会在 agent 写文件后同步给 language server。成功执行 Write 或 Edit 后，会触发： 

clearDeliveredDiagnosticsForFile
→ textDocument/didChange
→ textDocument/didSave
→ language server publishDiagnostics
→ LSPDiagnosticRegistry
→ attachments.ts (type: "diagnostics")
→ messages.ts expands to <new-diagnostics> system-reminder

诊断不再走已删除的 utils/attachments/lsp-diagnostics.ts，而是统一进入 attachment 管道：历史里保留 type: "attachment" 记录，发给模型前由 expandAttachmentMessagesForAPI 展开。

这意味着 agent 写完代码后，如果 language server 报类型错误、缺 import、STPL 语义问题等，下一步模型可以直接看到并继续修。
当前 getLSPDiagnosticAttachments 仅在工具集包含 Bash 时生效（与主线程可写环境对齐）；限流为每文件最多 10 条、总计 30 条，并按 delivered set 去重。

11. 限制和注意点

  • 当前是 agent 工具能力，不是网页编辑器的鼠标 hover 弹窗。
  • LSP tool 是 deferred，模型通常需要先通过 ToolSearch 激活。
  • Agent 侧只实现 stdio transport；STPL 的 TCP reverse-connect 由 bridge 完成，不是 HTTP/WebSocket LSP URL。
  • diagnostics 以 attachment / system-reminder 文本形式注入，暂未做前端专用诊断卡片。
  • LSP diagnostics 不能完全替代 npm run typecheck，复杂构建错误仍应跑项目命令验证。
  • 如果多个 server 支持同一扩展名，当前使用第一个匹配的 server。
  • 单文件超过 10MB 时 LSP tool 会拒绝分析。
  • STPL 依赖已启动的 SWC 与 JMX console；workspace 路径需与 Eclipse workspace 对齐。

12. 一句话总结

这个 LSP 实现给 coding agent 增加了“语义代码理解”和“写后诊断反馈”能力：模型通过 deferred LSP 工具同步询问语言服务器，写文件后异步收到 diagnostics attachment；对 STPL DSL，则通过 stpl-lsp-bridge 把 stdio 客户端接到 SWC JVM 内的 Language Server。
