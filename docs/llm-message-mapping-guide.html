4Attachment 消息（CC 对齐）

统一入口：utils/attachments.ts → getAttachmentMessages()。 History 原生存结构化 attachment；仅在 streamText 前展开为 LLM 可见的 user 消息。

4.1 存储格式（JSONL / 内存）

// core/types.ts — AttachmentMessage，与 role 消息并列于 Message union
{
  "type": "attachment",
  "uuid": "7b62084f-9bfd-445c-a09a-663a5cb1acd0",
  "timestamp": "2026-03-05T12:00:00.000Z",
  "isMeta": true,
  "attachment": {
    "type": "diagnostics",
    "files": [{ "uri": "/path/HelloWorld.java", "diagnostics": [...] }],
    "isNew": true
  }
}
JSONL 持久化： server/session.ts → appendMessage() 对 attachment 写 type: "attachment" 行（非 type: "message"）。 restoreFromDisk() 必须回放这两种 type，否则重载 session 会丢失 LSP / @文件 / plan 提醒。

4.2 注入时机（agent loop）

时机调用典型 attachment 类型
Turn 0（用户消息入列前） getAttachmentMessages(userMessage, ctx, messages) file、directory、pdf_reference（@提及）
每个 tool round 之后 getAttachmentMessages(null, ctx, messages) plan_mode、lsp diagnostics、plan_mode_exit
发 LLM 请求前 expandAttachmentMessagesForAPI(messages) 全部 attachment → role: "user", isMeta: true

4.3 Attachment 类型 → API 展开

attachment.type展开后形态代码
file / directory / pdf_reference 模拟 Read/Bash 的 tool_use + tool_result（包在 <system-reminder>） attachment-to-messages.ts
diagnostics <new-diagnostics>…</new-diagnostics>（非旧版 system-reminder 文案） utils/messages.ts → normalizeAttachmentForAPI
plan_mode / plan_mode_reentry / plan_mode_exit <system-reminder> 内 full/sparse plan 指令 utils/attachments/plan-mode.ts

4.4 LSP Diagnostic 管道

1passiveFeedback.ts 监听 textDocument/publishDiagnostics
2registerPendingLSPDiagnostic(workspaceKey, …) 写入 registry
3tool round 后 getLSPDiagnosticAttachments → checkForLSPDiagnostics
4产出 type: "diagnostics" attachment；Write/Edit 前 clearDeliveredDiagnosticsForFile
前置条件：仅当工具集含 Bash 时才注入 LSP diagnostics（与 CC 一致）。 Registry 按 workspaceKey 分区（多 cwd 场景）。

4.5 Plan mode 节流

每个 tool round 都会尝试注入 plan_mode，但多数轮次返回空数组。 getPlanModeAttachmentTurnCount 按 human turn 计数，不按 tool step 计数。

  • 同一用户 turn 内多 step：首次注入后 turnCount < 5 → 后续 step 不再注入
  • 跨 turn：距上次 plan_mode attachment 满 5 个 human turn 才再注入
  • plan_mode_reentry / plan_mode_exit：一次性事件

7System Prompt、Attachment 与 <system-reminder>

Anthropic / Claude Code

  • 全局指令 → 顶层 system
  • 上下文注入 → 结构化 Attachment，wire 前展开为 user 内容
  • LSP → <new-diagnostics> 包裹

OpenAI Responses

  • 全局指令 → instructions
  • Attachment 展开后 → 普通 user input items
  • Reasoning item 需 itemId replay（src 会 strip）

src 做法

  • systemPrompt → streamText({ system })
  • skillListing → 仍为 role: "user" + reminder（待 Phase 2 改 attachment）
  • Plan / LSP / @文件 → type: "attachment" 存入 history

8src 发给 SDK 前的五步预处理

入口：core/agent.ts → runOneStep()， 在 streamText({ messages }) 之前执行（顺序固定）。

1 inlineReasoningAsText — 把 reasoning part 转成 <thinking>…</thinking> 文本
2 expandAttachmentMessagesForAPI — type:"attachment" → normalizeAttachmentForAPI() → role:"user"（utils/messages.ts）
3 regroupToolResults — tool-result 挪到对应 assistant tool-call 之后
4 ensureToolResultPairing — 缺 result 合成 placeholder；删孤儿 result
5 applyCacheControlBreakpoint — Anthropic prompt caching
messageSanitize 与 attachment： regroupToolResults / ensureToolResultPairing 遇到 type: "attachment" 原样透传，不参与 tool 配对逻辑。
Synthetic result 文案： [Tool result missing due to internal error]

症状根因src 对策

12一句话速记

存储层：user / assistant / tool + CC 风格 type: "attachment"；JSONL 分 message / attachment 两种行。
API 层：attachment 在 streamText 前展开为 role: "user", isMeta: true；LSP 用 <new-diagnostics>。
Anthropic 只有 user / assistant； 工具结果是 user 里的 tool_result block，无 tool role。
OpenAI Responses 用扁平 input[]； Chat Completions 用 tool_calls + role: tool。
src：collect（getAttachmentMessages）与 expand（normalizeAttachmentForAPI）分离； tool round 后收集，发请求前展开 + sanitize。
