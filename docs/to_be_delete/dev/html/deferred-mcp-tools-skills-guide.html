Deferred MCP / Tools & Skill 懒加载

图文详解：为什么需要两套机制、数据流怎么走、messages 和 tools[] 各管什么

1发给 LLM 的一次请求 = 三条通道

很多人以为「加载工具」就是往 messages 里塞文字。实际上 schema 和对话是分开的。

图 1 · 三条通道职责不同：messages 记「说过什么」，tools[] 定「能调用什么」

2三种机制：延迟的是什么？

「Defer」在不同地方含义不同。Skill 不是 deferred tool pool，而是 body 懒加载。

🟡 Deferred 内置工具

  • 如 web_search、todo_write
  • 标记 shouldDefer: true
  • 延迟：Schema
  • 解锁：tool_search

🔵 Deferred MCP

  • 所有 MCP 工具默认 defer
  • 命名 {server}_{tool}
  • 延迟：Schema
  • 实例在 deferredToolPool

🟣 Skill 懒加载

  • skill 工具始终 active
  • 延迟：SKILL.md 正文
  • 解锁：调 skill(...)
  • 不用 discoveredTools

图 2 · 绿色 = 已在 active；红色 = 按需加载

3MCP 加载流程（tool_search → 下一步才能调）

用户：「用浏览器打开 example.com」

图 3 · MCP：tool result 是文字；Schema 进 tools[] 靠 activate，不靠 messages

⚠ 常见误解：Step 1 的 tool result 已经说「You can now use browser_navigate」，但同一步还不能调——必须等 Step 2 tools[] 更新。

图 5 · Skill body 出现在 tool result，不在 turn 开头的 listing 里

5为什么 messages 有了，还要 discoveredTools？

跨 Turn 时，prepareChatTurn 会重新 createSplit。没有 discoveredTools，MCP 又会被 defer 回去。

图 6 · messages 不能替代 discoveredTools：后者决定下一 Turn 的 tools[] 初始状态

✓ Skill 不需要这套：因为只有一个 skill schema，正文在 tool result 里模型就能继续执行；没有「每个 skill 一个独立 schema」的问题。

6一表总结

延迟什么 JSON Schema（tools[]） SKILL.md 正文

7一句话记住

Deferred 工具：messages 告诉模型「有个叫 X 的工具」；tools[] 才让它能真正调用 X。

Skill：listing 告诉模型「有个叫 xlsx 的流程」；调用 skill 后正文进 messages，模型按文字执行即可。
