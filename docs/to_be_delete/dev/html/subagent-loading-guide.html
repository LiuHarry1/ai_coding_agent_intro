1核心设计：数据 + 单一调度器

Subagent 不是「一堆独立 tool」，而是纯数据（AgentDefinition）+ 一个名为 Agent 的调度工具。 模型通过 subagent_type 参数选择类型，服务端再按定义裁剪工具集并启动一次隔离的 runAgent 循环。

图 1 · 单一 Agent 工具承载所有 subagent 类型；定义是数据，调度逻辑集中在 AgentTool.ts

src 的设计：所有 subagent 类型合并进一个 Agent 工具—— description 里列目录，schema 里用 subagent_type enum 选型。新增 agent 只改 AgentDefinition 数据（TS 或 Markdown），不必再注册新 tool。

2加载策略：两阶段 + 每轮热加载

Subagent 注册分两个阶段：进程启动时注册内置 trio；每次 chat 请求前重新扫描磁盘与插件，合并后覆盖 registry 上的 Agent 工具。 这样用户编辑 .ai-agent/agents/*.md 后下一轮立即生效，无需重启服务。

图 2 · 启动注册兜底 + 每轮 chat 前 merge 并重新 register Agent 工具

优先级规则（同名 agentType 后者覆盖前者）

来源路径sourceRank能否覆盖内置 trio

project <ancestor>/.ai-agent/agents/*.md（cwd → home） 2（最高） ✅ 可以（深层目录 > 浅层）
builtin tools/AgentTool/built-in/*.ts 基准层 — 默认存在，可被上层覆盖
信任边界（mergeAgents.ts）：插件 agent 不允许覆盖内置 Explore / Plan / general-purpose，冲突时忽略并 warn。 用户/项目级 agent 可以覆盖内置定义——适合在工作区 fork 定制 Explore 等行为。

3AgentDefinition：内置 TS vs Markdown

无论来源，最终都归一化为同一个 AgentDefinition 接口。内置 agent 用 TypeScript 工厂；自定义 agent 用带 YAML frontmatter 的 Markdown 文件。

Explore builtin

只读探索专家。disallowedTools 屏蔽写操作 + 交互工具 + 递归 Agent。omitProjectRules: true。

Plan builtin

只读架构规划。输出固定格式（Implementation Steps + Critical Files）。Plan 模式下 Phase 2 专用。

general-purpose builtin

继承父级几乎全部工具（含 write/edit/MCP），仅禁交互工具与 Agent 递归。适合需要改代码的多步任务。

Markdown agent 示例（工作区 .ai-agent/agents/*.md）

---
name: db-migrator
description: |
  Use when writing or applying SQL migrations...
tools: read_file, edit_file, write_file, grep, glob, bash
maxSteps: 25
label: DB
---

# Markdown body = subagent 的 systemPrompt
You are a database migration specialist...
Frontmatter 字段映射到说明
nameagentType必填；模型用作 subagent_type 值
descriptionwhenToUse必填；写入 Agent 工具 description 目录
bodysystemPromptMarkdown 正文，不能为空
toolsallow-list与 disallowedTools 互斥；自动剔除 Agent
disallowedToolsdeny-list默认还会加 INTERACTIVE_TOOLS + Agent
maxSteps / model / label同名可选字段控制子循环步数、模型、UI 标签
omitProjectRulesbooleantrue 时不注入 AGENTS.md 等项目规则

4调用流程：从模型 tool call 到子 runAgent

主 agent 在 tool schema 里看到 subagent_type enum（所有已注册 agentType）和详细 usage notes。 一次 Agent 调用 = 启动一个全新 agent 循环，不继承父对话 history。

图 3 · Subagent 调用链：查定义 → 事件总线隔离 → 裁剪工具 → 空 messages 启动子 runAgent

1
模型发起 tool call Agent({ subagent_type: "Explore", description: "...", prompt: "..." }) — prompt 必须自包含，子 agent 看不到父对话。
2
校验与 Plan 模式限制 Plan 模式仅允许 Explore（Phase 1）和 Plan（Phase 2）；其他类型直接返回 Error 字符串。
3
Scoped EventBus createSubagentEventBus(parent, parentToolCallId, scopeLabel) — 所有子事件带 parentToolCallId，前端 SubagentCard 可嵌套展示；同轮并行多个 subagent 时靠此路由。
4
工具集裁剪 有 tools → allow-list；否则 full registry 再按 disallowedTools 删除。始终删除 Agent（防递归 spawn）。
5
runAgent 子循环 messages: [] 从零开始；maxSteps 默认 20（各 agent 可 override）；返回 finalText 作为 tool result 给父 agent。

Tool call 参数 schema（自动生成）

inputSchema = z.object({
  subagent_type: z.enum(["Explore", "Plan", "general-purpose", ...]),  // 来自 merge 后的 agent 列表
  description:   z.string().min(1),   // UI 短标题
  prompt:        z.string().min(1),   // 完整任务描述
});

5createTaskTool 工具提示词长什么样？

主 agent 看到的不是 subagent 各自的 system prompt，而是一个名为 Agent 的工具描述（tool description）。 它在 createTaskTool(agents) 里由固定文案模板 + 动态 agent 目录拼成，并同时写入 ToolDefinition.description 与 AI SDK tool({ description })。

图 5 · AgentTool.ts 第 32–98 行：目录来自各 agent 的 whenToUse，其余为硬编码引导语

拼装规则

区块来源作用
Available agent types: 列表 动态 · 每个 AgentDefinition - {agentType}: {whenToUse} (Tools: …)；Tools 行由 tools allow-list 或 disallowedTools deny-list 生成
开头 + When NOT to use 静态模板 引导主 agent 优先用 Read / Glob 做窄查询，别滥用 subagent
Usage notes 静态模板 并行 dispatch、隔离上下文、结果需父 agent 转述给用户、可 proactive 使用
Writing the prompt 静态模板 教主 agent 怎么写 prompt：像 briefing 新同事，禁止 terse command
<example> 块 静态模板 + Explore/Plan 常量名 few-shot：何时选 Explore vs Plan
subagent_type enum 动态 · validTypes Zod .enum([...])，与目录里的 agentType 一一对应

动态目录行格式（代码）

// AgentTool.ts L32–40
const directory = agents.map((a) => {
  const toolsDesc = a.disallowedTools?.length
    ? `All tools except ${a.disallowedTools.join(", ")}`
    : a.tools?.length
      ? a.tools.join(", ")
      : "All tools";
  return `- ${a.agentType}: ${a.whenToUse} (Tools: ${toolsDesc})`;
}).join("\n");

下面是主 LLM 实际读到的 Agent 工具 description 示意（自定义 .md agent 会在列表末尾追加同样格式的行）：

Launch a new agent to handle complex, multi-step tasks autonomously.

The Agent tool launches specialized agents (subprocesses) that autonomously handle complex tasks. Each agent type has specific capabilities and tools available to it.

Available agent types:
- Explore: Fast agent specialized for exploring codebases. Use this when you need to quickly find files by patterns … (Tools: All tools except Write, Edit, TodoWrite, AskUserQuestion, Agent)
- Plan: Software-architect subagent for designing implementation plans before code is written. Use proactively for non-trivial changes … (Tools: All tools except Write, Edit, TodoWrite, AskUserQuestion, Agent)
- general-purpose: General-purpose subagent for open-ended research and multi-step tasks … (Tools: All tools except AskUserQuestion, Agent)

When using the Agent tool, specify a `subagent_type` parameter to select which agent type to use.

When NOT to use the Agent tool:
- If you want to read a specific file path, use `Read` or `Glob` instead …
- If you are searching for a specific class definition like "class Foo", use `Glob` instead …
- If you are searching for code within a specific file or set of 2-3 files, use `Read` instead …
- Other tasks that are not related to the agent descriptions above

Usage notes:
- Always include a short `description` (3-5 words) summarizing what the agent will do.
- You can issue several `Agent` calls in one response to dispatch independent agents in parallel …
- Each invocation starts fresh — the subagent does NOT see your prior conversation. The `prompt` must be self-contained.
- The subagent returns a single final report. The result is NOT visible to the user — summarize the relevant parts in your own reply.
- The subagent's outputs should generally be trusted. Don't re-run the same searches yourself.
- Clearly tell the subagent whether you expect it to write code or just research …
- If the agent description mentions that it should be used proactively, then you should try your best to use it without the user having to ask …

Writing the prompt — brief the subagent like a smart colleague who just walked into the room …
- Explain what you're trying to accomplish and why.
- Describe what you've already learned or ruled out.
- Give enough context about the surrounding problem …
- Be specific about scope and the form of answer you want …
- Lookups: hand over the exact command. Investigations: hand over the question …
- Never delegate understanding. Don't write "based on your findings, fix the bug" …

Terse command-style prompts produce shallow, generic work.

Examples:

"Explore": use this agent for exploring and understanding codebases
"Plan": use this agent to design implementation plans before writing code
</example_agent_descriptions>

参数 schema 上的「第二层提示词」

除 tool description 外，每个参数字段还有 Zod .describe()，会进入 JSON schema 供模型读：

参数类型.describe() 原文
subagent_type z.enum(validTypes) Which subagent to dispatch to. Must be one of the registered agent types.
description z.string().min(1) Short 3-5 word title for the task, shown in the UI.
prompt z.string().min(1) Self-contained, detailed task description. The subagent does NOT see prior conversation, so include all needed context, file paths, and what to return.
和 subagent system prompt 的分工：上面整段 description 只给主 agent，教它「何时 dispatch、怎么写 prompt」。 Subagent 真正执行时用的是 AgentDefinition.systemPrompt（+ 可选 project rules），由 runAgent(..., { systemPrompt: subSystemPrompt }) 注入，不会再看到这段 Agent 工具 description。

源码：src/tools/AgentTool/AgentTool.ts · 工具名常量 AGENT_TOOL_NAME = "Agent"

6工具权限策略

Subagent 不会继承父 agent 当轮的 tool 快照，而是根据 AgentDefinition 从 registry 重新 createAll，再应用 allow/deny 规则。

Agent策略典型可用明确禁止
Explore deny-list glob, grep, read_file, bash(只读) MUTATING_TOOLS, INTERACTIVE_TOOLS, Agent
Plan deny-list 同 Explore 同上
general-purpose deny-list（宽松） 读写删改 + MCP + bash INTERACTIVE_TOOLS, Agent
Markdown（默认） deny-list 默认 除交互/Agent 外全部 INTERACTIVE_TOOLS, Agent（可用 tools: 收紧）
Markdown（tools:） allow-list 仅列出的工具 Agent 自动剔除
并发策略：Agent 工具标记 isConcurrencySafe: () => false——同一步内多个 subagent tool call 会串行执行，避免 registry / 文件系统竞态。 模型仍可在一条回复里发出多个 Agent 调用（并行 dispatch 意图），由 executor 排队。

10设计要点回顾

Single-Task 架构

一个 Agent 工具 + N 份数据定义。新增 subagent = 加 .md 或 TS 定义，无需新 tool 注册点。

热加载

每 chat turn 重新 scan + merge + register。开发体验友好，与 skills 注册策略对称。

隔离执行

空 messages、独立 event bus、裁剪工具集、禁递归 Agent。子 agent 是「同事刚进门」——靠 prompt briefing，不是共享上下文。
